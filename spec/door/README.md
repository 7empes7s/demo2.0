# Door credential format and vectors, v1

What a verifier needs to check a Door presentation, and what `vectors.json` contains.
`modules/door` (Rust) is the only implementation; the vectors are generated by it.

> `vectors.json` is **generated by this code from public test seeds**. It is not a set of
> fixtures from another implementation or from the IRTF drafts. It shows that the implementation
> agrees with itself over time (the drift test in `modules/door/tests/vectors.rs`), not that it
> interoperates with anyone. The seeds in it are public and must never be used for a real Door.

All hex is lowercase. Byte lengths are exact and enforced before decoding.

## 1. Primitives

| Piece | Standard | Suite |
|---|---|---|
| Signature, proof | draft-irtf-cfrg-bbs-signatures-12 | `BBS_BLS12381G1_XMD:SHA-256_SSWU_RO_` |
| Blind issuance | draft-irtf-cfrg-bbs-blind-signatures-02 | same |
| Pseudonym | draft-irtf-cfrg-bbs-per-verifier-linkability-03 | same, API id suffix `H2G_HM2S_PSEUDONYM_` |
| Uniqueness key | RFC 9497 OPRF | ristretto255-SHA512, `info = "d2.door.uniqueness/1"`, input `"d2.door.person/1" 0x00 person_id` |

Note: the implementation (`zkryptium` 0.7.1) computes the blind signature's `B` value from the
base point `P1` instead of the draft's `Q_1`, so the signature bytes do not match a
draft-exact implementation. Proof verification is consistent within this implementation.

## 2. Credential

Header: `"d2.door.credential/1"` (signed into every signature and proof).

Seven signer-known messages, in this order, each an ASCII string:

| index | message | notes |
|---|---|---|
| 0 | `jurisdiction.0=<level 0>` | e.g. `jurisdiction.0=lu` |
| 1 | `jurisdiction.1=<levels 0-1>` | e.g. `jurisdiction.1=lu.esch`, or `jurisdiction.1=` if the path is shorter |
| 2 | `jurisdiction.2=<levels 0-2>` | |
| 3 | `jurisdiction.3=<levels 0-3>` | |
| 4 | `adult=true` or `adult=false` | |
| 5 | `epoch=<decimal>` | |
| 6 | `rid=<64 hex>` | revocation handle; never disclosed |

A jurisdiction path has 1 to 4 levels of `[a-z0-9-]+` joined by `.`. After these messages the
blind-signatures draft appends the holder's blinding factor and the per-verifier draft appends
one pseudonym secret, so a signature covers 9 scalars.

Holder commitment (`commitment_with_proof`): exactly **144 bytes** (48-byte G1 point, then
`s_cap`, one `m_cap`, challenge; 32 bytes each). Blind signature: 80 bytes.

## 3. Issuer key

```json
{ "epoch": 1, "bbs_public_key": "<192 hex, compressed G2>", "ciphersuite": "BBS_BLS12381G1_XMD:SHA-256_SSWU_RO_",
  "valid_from": "2026-01-01T00:00:00Z", "valid_to": "2026-12-31T23:59:59Z" }
```

Derived from key material with `key_info = "d2.door.issuer/1 epoch=<epoch>"` (BBS KeyGen).

## 4. Presentation

```json
{
  "epoch": 1,
  "context": "agora:lu.esch",
  "challenge": "<hex of the verifier's challenge>",
  "disclosed": { "jurisdiction_path": "lu.esch", "adult": true, "epoch": 1 },
  "pseudonym": "<96 hex, compressed G1>",
  "proof": "<hex>"
}
```

- `context` is the per-verifier `context_id` of the pseudonym draft, as bytes of the string.
- `challenge` is the proof's presentation header `ph`.
- `disclosed` lists what was revealed; each present field maps back to messages: a path of `d`
  levels discloses indexes `0..d`, `adult` index 4, `epoch` index 5. Indexes ascending.
- `pseudonym = hash_to_curve(context) * nym_secret`; the short form used by other modules is
  `nym-` + first 26 characters of lowercase base32 (RFC 4648, no padding) of SHA-256(point).
- `proof` is the per-verifier draft's proof: 3 G1 points (144 bytes), then `e_cap`, `r1_cap`,
  `r3_cap`, one `m_cap` per undisclosed scalar, and the challenge (32 bytes each). With `k`
  disclosed messages its length is exactly `144 + 32 * (3 + (9 - k) + 1)` bytes.

## 5. Verification

In this order, stopping at the first failure:

| check | error |
|---|---|
| `epoch` equals the issuer key's epoch | `epoch_mismatch` |
| `context` equals the verifier's context | `context_mismatch` |
| `challenge` equals the challenge the verifier issued | `challenge_mismatch` |
| `disclosed` covers what the verifier requires | `missing_disclosure` |
| key, disclosed messages, proof length and pseudonym decode | `malformed` |
| `ProofVerifyWithNym(pk, proof, header, ph, pseudonym, context, 1, L = 7, disclosed messages and indexes)` | `invalid_proof` |

On success the verifier learns the pseudonym and the disclosed attributes, nothing else.

## 6. vectors.json

| field | content |
|---|---|
| `schema` | `d2.door.vectors/1` |
| `generated_by`, `warning`, `ciphersuite`, `drafts`, `credential_header` | provenance |
| `seeds` | the public test seeds (`issuer`, `oprf`, `other_issuer`), each `SHA-256("d2.door test seed: <label>")` |
| `issuer_keys` | epochs 1 and 2 from `seeds.issuer`; deterministic, regenerated by the drift test |
| `uniqueness` | `u` for the three demo people from `seeds.oprf`; deterministic |
| `second_enrolment` | the same person's second token refused with `already_enrolled` |
| `credentials` | the three demo credentials with the seeds they came from (randomised: recorded and re-verified) |
| `pseudonyms` | each credential's pseudonym in three contexts; deterministic given the credential |
| `presentations` | 18 cases: 5 that verify (with the exact `disclosed` result) and 13 that must fail with the named error: wrong epoch key, forged epoch, another issuer's key, tampered adult, tampered jurisdiction, replay to another context (plain and forged), replay against another challenge (plain and forged), missing disclosure, swapped pseudonym, truncated proof, flipped proof bit |

Regenerate only when the format changes: `cargo run -p d2-door -- vectors --out spec/door/vectors.json`.
Check: `cargo run -p d2-door -- check spec/door/vectors.json`.
